## 2026-07-16 — Step 2: Data Simulation Engine, complete

What was done: Built every generator named in Step 2's key-tasks list under `backend/app/simulation/`, and authored the real scenario library from them.

`gas_process.py` implements the OU gas simulator exactly per `CORRIX_DATA_METHODOLOGY.md` §3.2-§3.3: a standalone `step()` function (Euler-Maruyama, reused unmodified by Step 8's Monte Carlo forecaster) and the three source-term shapes (ramp, step-decay, ramp-with-plateau). `GasSignalConfig` (Step 1's schema) needed extending with three fields the doc describes narratively but doesn't name (`secondary_trigger_minute`, `secondary_rise_minutes`, `secondary_magnitude`) to make the ramp-with-plateau shape's "secondary compounding ramp" concrete. `compliance_process.py` implements S1's Q(t) model per §4 as a fully separate module: a lapse is sampled at most once per run (Bernoulli, per-tick), probability elevated near shift-changeover proximity, degrading the score once and permanently — kept deliberately not-the-gas-model, per the doc's explicit instruction.

`plant_layout.py` loads a hand-authored `data/layout/plant_layout.json`: the eight zones from §7's table (hazard classes, confined-space/assembly-point flags) plus an adjacency edge list connecting all eight zones in one component, with both assembly points (Z4, Z8) reachable from every zone — needed for Step 8's evacuation routing later, cheaper to get right now.

`permit_generator.py`, `shift_generator.py`, and `worker_location_generator.py` each produce a background-traffic stream (so the plant looks busy, per §5/§6, and so negative controls have realistic non-scenario activity) plus a scenario-specific injection function. Hit and fixed a real bug during this work: `numpy.random.Generator.choice` on a list of Pydantic/Enum objects silently coerced them to their `str()` representation instead of returning the object itself (e.g. `PermitType.ELECTRICAL_ISOLATION` became the literal string `"PermitType.ELECTRICA"`, truncated, and failed Pydantic validation) — fixed by switching to index-based selection (`rng.integers`/`rng.choice(len(...))`) everywhere a non-numeric collection is sampled.

`scenario_engine.py` ties all of the above into `run_scenario(config) -> ScenarioOutput`, fully deterministic since every generator it calls is itself seeded from `config.seed`. It deliberately does not synthesize `CVObservationEvent` objects from a scenario's `cv_event` config block — that would fabricate simulated data under the `source: "real_inference"` label the Step 1 schema restricts to genuine CV inference output (§9's real/simulated honesty split), so the block is left as metadata for Step 6's live correlation layer to read at demo time, not something Step 2 invents.

The real scenario library was authored via `backend/scripts/author_scenario_configs.py` (a regeneration convenience, not a runtime dependency — the committed YAML files are the source of truth, per §16): 20 positive instances (S1 anchor/compliance in Z1, S2 confined-space ramp-with-plateau in Z7, S3 maintenance/gas ramp in Z2, S4 hot-work step-decay in Z2), 5 seed variants each, split 3 `population` / 2 `held_out` per §12.5, plus 20 matched negative-control instances (`data/scenarios/negative/`, cycling across all 8 zones, same split ratio, `signals: {}`, sentinel ground-truth values documented in the scenarios README). Gas-signal parameters (`a`, `k`, `t0`, `tau`, etc.) for S2-S4 were tuned empirically by running the simulator and checking the resulting curve actually crosses the real 10%-LEL alarm threshold at a sensible time relative to the scripted permit/shift/worker-location timing — not just plugged in from the doc's illustrative formulas without checking the output. S1's compliance-lapse coupling needed retuning for the same reason: the first parameter choice (`p_boost=0.02`) produced a lapse in only about half of seed variants by chance, which would make an authored "positive" scenario an unreliable demonstration; boosted to `p_boost=0.15` so the scripted lapse reliably occurs near shift-changeover across all seed variants — a deliberate choice that this is a scripted narrative scenario, not a model of how rare the real-world lapse should be.

Verification: 129 backend tests pass, including a 90-test sweep (`test_scenario_library.py`) that runs every single authored config (all 40 files) through `run_scenario` and checks determinism, schema validity, matched positive/negative volume (20 and 20), valid `memory_split` on every file, the scripted worker actually showing up in the scripted permit's zone during its active window for every S1 seed, and per-scenario-type shape-trend correctness (S3 rises, S4 peaks-then-decays, S2 plateaus-then-rises). ## 2026-07-16 — Step 3: Core Detection Layer (Fast Path), complete

What was done: Built the anomaly scorer, the permit-conflict rule table, the event-trigger condition, and wired both MCP servers to call real code, all under `backend/app/detection/`.

The anomaly scorer went through a real correction during this step. The first implementation (`rolling_zscore`) computed each point's z-score against a trailing window of recent readings — the textbook definition of "rolling z-score." Checked against the actual Step 2 scenario library rather than trusted on unit tests alone, it had a 100% false-positive rate: every one of the 20 negative controls hit HIGH or CRITICAL, at every window size tried (60 to 600 ticks). Root cause: the OU gas process is strongly autocorrelated (mean-reversion time constant ~12 minutes), so a short trailing window's own mean/std reflects the process's local smoothness rather than its true normal-operating spread — neighboring ticks aren't independent samples, so the window looks artificially tight and any ordinary reading spikes the z-score. Replaced with a calibrated-baseline approach (`baseline_calibrated_zscore`): mean/std fit once from the first ~8 minutes of each run (before any scripted event's earliest `t0_minute`), then every subsequent reading scored against that fixed reference. Checked empirically against the full library: negative controls now top out around \|z\|=12, positive scenarios start around \|z\|=84 — a wide, clean separation. Thresholds set at CAUTION=6, HIGH=20, CRITICAL=50 with that empirical gap in mind, not arbitrary round numbers.

That same investigation surfaced a real gap left over from Step 2: negative controls had `signals: {}` entirely, meaning no gas or compliance reading series existed at all — nothing for the anomaly scorer to score. `CORRIX_DATA_METHODOLOGY.md` §12.4 specifies negative controls should run the identical generators with `S(t)=0`, i.e. the OU process should still run, baseline plus noise only, not be entirely absent. Fixed by regenerating all 20 negative-control configs with a `GasSignalConfig` carrying `a=0.0` (a source term of exactly zero realizes "S(t)=0" per the model's own formula), baseline concentration set per zone hazard class. This was a correction to Step 2's authored output, made and recorded here rather than silently folded backward into the Step 2 entry, per `CLAUDE.md` Section 5's instruction that the log should show real history, including reversals.

`permit_conflict.py` implements the deterministic rule table: an active permit in a zone conflicts once the zone's current anomaly risk_level clears a hazard-class-dependent bar (HIGH-hazard zones: CAUTION; MEDIUM-hazard zones: HIGH; LOW-hazard zones never conflict). Deliberately gated on hazard class and risk level only, not permit type, generalizing the build plan's named example (hot work) to cover S3's cold-work-permit-near-gas pattern too — the brief's own maintenance/gas co-occurrence risk isn't specific to hot work. Permit type is still recorded in the conflict's reason string for explainability.

`trigger.py` defines the actual event-trigger condition (anomaly HIGH/CRITICAL or permit conflict) as a plain function, not a Council agent — the fast-path trigger is explicitly allowed to see both sensor and permit data at once; the agent-silo constraint (`CORRIX_PROJECT.md` §6.1) applies to the Council's five agents starting in Step 4, not to this deterministic baseline.

Both the Sensor Stream and Permit/Shift MCP servers now call this real detection code instead of returning stub data, taking `scenario_id`/`seed`/`zone_id` (plus `at_minute` where relevant) as parameters, since there's no live-running plant state yet (that's Step 9). `check_permit_conflict`'s tool signature takes `risk_level` as an explicit argument the caller supplies, rather than the Permit/Shift server reaching into Sensor Stream's data itself — kept consistent with the silo design even though no agents exist yet to enforce it structurally.

Verification: 239 backend tests pass. Checked against the real scenario library, not just synthetic examples: all 20 positive scenario instances (S1-S4) reach HIGH/CRITICAL and trigger with positive lead time (7.75 to 77 minutes before their scripted incident threshold, varying by scenario type); all 20 negative controls never flag HIGH/CRITICAL and never trigger; the permit-conflict checker correctly flags the scripted conflict at peak anomaly for every one of the 20 positive instances. Both MCP tools were also called manually end to end (not just via pytest) and returned correct real data: `get_anomaly_score` reported CRITICAL for S1, `check_permit_conflict` correctly flagged the scripted lifting-operation permit, `get_shift_status` correctly reported 8 minutes to changeover at minute 60 of a scenario with `changeover_at_minute=68`.

Why: Step 3's stated goal is a fast path that both triggers the Council later and serves as the Evaluation Harness's baseline — a detector calibrated to cry wolf on every quiet day would poison both purposes, so getting the false-positive behavior right now (rather than deferring it to Step 8's harness to discover) was worth the extra diagnostic work.
