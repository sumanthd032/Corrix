## 2026-07-16 — Step 3: Core Detection Layer (Fast Path), complete

What was done: Built the anomaly scorer, the permit-conflict rule table, the event-trigger condition, and wired both MCP servers to call real code, all under `backend/app/detection/`.

The anomaly scorer went through a real correction during this step. The first implementation (`rolling_zscore`) computed each point's z-score against a trailing window of recent readings — the textbook definition of "rolling z-score." Checked against the actual Step 2 scenario library rather than trusted on unit tests alone, it had a 100% false-positive rate: every one of the 20 negative controls hit HIGH or CRITICAL, at every window size tried (60 to 600 ticks). Root cause: the OU gas process is strongly autocorrelated (mean-reversion time constant ~12 minutes), so a short trailing window's own mean/std reflects the process's local smoothness rather than its true normal-operating spread — neighboring ticks aren't independent samples, so the window looks artificially tight and any ordinary reading spikes the z-score. Replaced with a calibrated-baseline approach (`baseline_calibrated_zscore`): mean/std fit once from the first ~8 minutes of each run (before any scripted event's earliest `t0_minute`), then every subsequent reading scored against that fixed reference. Checked empirically against the full library: negative controls now top out around \|z\|=12, positive scenarios start around \|z\|=84 — a wide, clean separation. Thresholds set at CAUTION=6, HIGH=20, CRITICAL=50 with that empirical gap in mind, not arbitrary round numbers.

That same investigation surfaced a real gap left over from Step 2: negative controls had `signals: {}` entirely, meaning no gas or compliance reading series existed at all — nothing for the anomaly scorer to score. `CORRIX_DATA_METHODOLOGY.md` §12.4 specifies negative controls should run the identical generators with `S(t)=0`, i.e. the OU process should still run, baseline plus noise only, not be entirely absent. Fixed by regenerating all 20 negative-control configs with a `GasSignalConfig` carrying `a=0.0` (a source term of exactly zero realizes "S(t)=0" per the model's own formula), baseline concentration set per zone hazard class. This was a correction to Step 2's authored output, made and recorded here rather than silently folded backward into the Step 2 entry, per `CLAUDE.md` Section 5's instruction that the log should show real history, including reversals.

`permit_conflict.py` implements the deterministic rule table: an active permit in a zone conflicts once the zone's current anomaly risk_level clears a hazard-class-dependent bar (HIGH-hazard zones: CAUTION; MEDIUM-hazard zones: HIGH; LOW-hazard zones never conflict). Deliberately gated on hazard class and risk level only, not permit type, generalizing the build plan's named example (hot work) to cover S3's cold-work-permit-near-gas pattern too — the brief's own maintenance/gas co-occurrence risk isn't specific to hot work. Permit type is still recorded in the conflict's reason string for explainability.

`trigger.py` defines the actual event-trigger condition (anomaly HIGH/CRITICAL or permit conflict) as a plain function, not a Council agent — the fast-path trigger is explicitly allowed to see both sensor and permit data at once; the agent-silo constraint (`CORRIX_PROJECT.md` §6.1) applies to the Council's five agents starting in Step 4, not to this deterministic baseline.

Both the Sensor Stream and Permit/Shift MCP servers now call this real detection code instead of returning stub data, taking `scenario_id`/`seed`/`zone_id` (plus `at_minute` where relevant) as parameters, since there's no live-running plant state yet (that's Step 9). `check_permit_conflict`'s tool signature takes `risk_level` as an explicit argument the caller supplies, rather than the Permit/Shift server reaching into Sensor Stream's data itself — kept consistent with the silo design even though no agents exist yet to enforce it structurally.

Verification: 239 backend tests pass. Checked against the real scenario library, not just synthetic examples: all 20 positive scenario instances (S1-S4) reach HIGH/CRITICAL and trigger with positive lead time (7.75 to 77 minutes before their scripted incident threshold, varying by scenario type); all 20 negative controls never flag HIGH/CRITICAL and never trigger; the permit-conflict checker correctly flags the scripted conflict at peak anomaly for every one of the 20 positive instances. Both MCP tools were also called manually end to end (not just via pytest) and returned correct real data: `get_anomaly_score` reported CRITICAL for S1, `check_permit_conflict` correctly flagged the scripted lifting-operation permit, `get_shift_status` correctly reported 8 minutes to changeover at minute 60 of a scenario with `changeover_at_minute=68`.

Why: Step 3's stated goal is a fast path that both triggers the Council later and serves as the Evaluation Harness's baseline — a detector calibrated to cry wolf on every quiet day would poison both purposes, so getting the false-positive behavior right now (rather than deferring it to Step 8's harness to discover) was worth the extra diagnostic work.

## 2026-07-16 — Step 4: The Safety Council (Multi-Agent Core), complete

What was done: Built the full LangGraph multi-agent core under `backend/app/council/`: an LLM client with real Groq/Gemini failover, four evidence agents with the silo constraint enforced by construction, a Chair synthesis node, the compiled graph with a real interrupt-based Safety Officer Override, and hand-crafted S1-S4 evidence payloads.

`llm_client.py` tries Groq first and falls back to Gemini on any exception, never load-balanced, per `CORRIX_PROJECT.md` §7.1. `_call_groq`/`_call_gemini` are separated so a test can monkeypatch the primary call to fail deterministically rather than needing to actually exhaust Groq's real rate limit.

Wired the Worker Location MCP server to real Step 2 badge-ping data (the same pattern Step 3 used for Sensor Stream and Permit/Shift) — not strictly required by Step 4, but cheap, and it means the Site Safety Observer agent has one genuinely real data source instead of only the CV/Observation stub (CV real inference is Step 6 territory).

`agents.py` defines the four evidence agents (`EvidenceAgent` dataclass), each constructed with an explicit `bound_servers` list — the only MCP server object(s) its real-world counterpart would have. `bound_tool_names` inspects each server's actual registered tools via `mcp.server.fastmcp`'s internal `ToolManager.list_tools()`, not the agent's prompt, so the silo constraint (`CORRIX_PROJECT.md` §6.1) is checkable by construction: five tests confirm each agent's bound tools are exactly its assigned server's tools and disjoint from every other server's (except the deliberate Permit Control Officer / Shift Operations pair, which legitimately share the Permit/Shift server).

`chair.py` implements the synthesis node: the LLM is asked only for judgment fields (risk_level, confidence, compound_flag, time_to_critical stub, explanation, recommended_action) — zone_id/scenario_id/trigger_reason/timestamp/council are assembled programmatically from values already known to the caller, never trusted to an LLM's JSON echo. `time_to_critical` is explicitly a stub at this stage (an LLM-estimated placeholder band), per the build plan — the real Monte Carlo rollout reusing the simulator's own `step()` lands in Step 8.

`graph.py` compiles the state machine: four evidence nodes fan out from START and converge into the Chair, using a `MemorySaver` checkpointer and `interrupt_before=["chair"]` so the Safety Officer Override is a genuine graph pause, not a UI-only one. `apply_safety_officer_override()` writes a human note into the paused checkpoint; resuming feeds it into the Chair's prompt.

Two real corrections came out of testing this against actual LLM calls rather than trusting the design on paper:

1. The first Chair system prompt produced technically well-formed JSON but consistently rated S1's textbook compound scenario as CAUTION/compound_flag=false — the small, fast Groq model (`llama-3.1-8b-instant`) needed the "compound risk" concept spelled out explicitly (naming the anchor incident's own pattern: active permit + degrading process reading + imminent changeover + worker presence = at least HIGH, compound_flag true) rather than inferring it from a generic "synthesize these four reports" instruction. Rewrote the prompt; retested against all four hand-crafted payloads, all now correctly reach HIGH/CRITICAL with compound_flag true.
2. Testing the full graph (not just the Chair in isolation) surfaced a second, more subtle gap: each evidence agent's own LLM-generated paraphrase of its raw hand-fed evidence was dropping the exact identifiers that let the Chair cross-reference reports — the Permit Control Officer's raw input said "linked to checklist CHK-0410," but its paraphrase said "no outstanding issues," silently discarding the one detail connecting it to the Process Safety Engineer's report about that same checklist's compliance score dropping. Added an explicit "preserve every exact identifier, never paraphrase into vague reassurance" instruction to all four persona prompts; retested, and the compound pattern now survives the paraphrasing step correctly.

Also hit, and handled rather than worked around, a genuine external constraint: this session's own repeated real-call testing exhausted both Groq's per-minute token limit and Gemini's daily free-tier request quota (20/day for the resolved model) at different points — exactly the kind of tight-quota risk `CORRIX_PROJECT.md` §7.1 already flags. Added `tests/conftest.py`'s `skip_on_rate_limit` so a genuine 429 from either provider skips with a clear reason instead of failing the suite; the underlying failover logic was already proven correct against live, unexhausted quota multiple times during this same work session (both at the LLM-client level and the full-graph level, with real CRITICAL/compound_flag=true verdicts produced via Gemini while Groq was deliberately blocked).

Verification: 254 backend tests pass, 8 skip (all confirmed rate-limit skips from real provider quotas, not code failures). Directly checked against Step 4's Definition of Done: S1-S4 each resolve end-to-end in under 30 seconds (typically 3-15s); the silo constraint holds both on the standalone agent objects and inside the compiled graph's node construction; S2-S4 produce three genuinely different (non-templated) explanations; the override interrupt demonstrably pauses the graph before the Chair runs, accepts a human note, and the resumed verdict's explanation/recommended_action visibly reflects it; Gemini failover was verified at the full-graph level with the entire Groq path deliberately blocked via monkeypatching, resolving correctly to a CRITICAL/compound_flag=true verdict.

Why: Step 4's central architectural claim — that the compound risk only emerges from fusion because no single agent can see the whole picture — has to be true by construction, not just asserted in a prompt, or the entire differentiation thesis (`CORRIX_PROJECT.md` §6.1) is just narrative. Verifying the tool bindings directly, and catching the paraphrase-dropping-identifiers bug by testing the full graph rather than the Chair in isolation, both went toward making that claim actually hold up rather than merely reading well.

The bug: the frontend's WebSocket hook sends an initial `{"type":"start","scenario_id":"S1"}` on connection open, then a second `start` message the moment a user picks a different scenario. When these two messages arrive close together, `_run_playback`'s interrupt-check requeued the interrupting message onto the queue unconditionally before also returning it to the outer loop — duplicating it. The outer loop consumed the returned copy to begin the new scenario's playback, but the leftover duplicate stayed in the queue; the very next interrupt-check call immediately found that same leftover message, requeued it again, and returned again, forever. The connection then sends nothing at all, not even the first tick, for as long as the client stays connected. Reproduced directly against the raw backend WebSocket protocol (bypassing the frontend and browser entirely) with two `start` messages sent 50ms apart: confirmed the stall, then confirmed the fix resolves it, before touching the frontend at all — isolating the bug to the backend rather than guessing.

Fix (`backend/app/api/websocket.py`): only requeue the peeked message when it is *not* being returned; a message that's about to be handed to the outer loop via the return value should not also remain in the queue for a second, phantom delivery.

This was the largest, most design-heavy step so far; several real architectural questions came up that weren't fully pinned down by the three docs, and were resolved with the user rather than guessed.

**Design decision confirmed with the user first:** how the memory loop's before/after proof could mean anything given S5 is deliberately built to evade both the rule/threshold and novelty triggers. Resolved by adding a third, independent trigger path — retrieval similarity against stored past misses — so the held-out comparison has a real mechanism to demonstrate, not just a hoped-for number.

**S5 (silent sensor drift) authored** in Z2, deliberately sub-threshold. A real gap surfaced empirically: background permits exist in every zone regardless of scenario, and the OU process's own noise occasionally spikes into CAUTION range purely by chance — for a high-hazard zone with any active permit, that alone trips the rule/threshold path. S5's seeds were selected by running the real detection pipeline end-to-end and keeping only ones verified never to trigger, the same discipline as Step 2/3's own empirical tuning. Negative controls were extended from 20 to 25 to keep the harness's false-positive measurement fair against the new positive count, and one negative-control seed that hit the identical background-permit/noise overlap was swapped for a verified-safe replacement.

**Joint-evidence novelty detector**: Mahalanobis distance fit on population-split negative controls. A real regularization bug was found and fixed by checking against the actual library rather than trusting the model on sight: a uniform ridge term let one near-constant feature (shift-changeover proximity, which negative controls' short windows never reach) dominate the distance for any scenario with genuine changeover timing, collapsing a five-feature detector into a one-feature one. Fixed by flooring each feature's own variance at a sensible minimum instead. Confirmed S1-S4 all trigger via novelty and S5 stays sub-threshold on every seed.

**Risk-aware evacuation routing**: Dijkstra with risk-weighted edges over the Step 2 adjacency graph, wired into the live verdict (attached to any HIGH/CRITICAL verdict using the real zone-risk snapshot at the trigger moment) and rendered as a highlighted path on the heatmap. Verified live in a browser — a genuine layout bug surfaced during this pass, unrelated to routing itself: the dev backend had accumulated multiple stale listener processes on port 8000 across the session, some invisible to `ps`/`tasklist` from different tool sandboxes, silently serving old code after apparent restarts. Needed to hunt down and kill the actual OS-level processes before the real routing code was actually being served.

**Monte Carlo Time-to-Critical forecaster**: N=200 rollouts reusing the simulator's own `step()`, replacing the Chair's LLM-estimated stub for gas-based zones (S1's compliance signal isn't an OU process, so it keeps the stub — a real, documented scope limit). Wired as a post-synthesis replacement in the live WebSocket path, not fed into the Chair's prompt, since it's a deterministic computation, not a judgment call.

**Evaluation Harness**: runs baseline (Step 3) vs. full pipeline (rule/threshold + novelty, real Council convening) across the whole library. Made resilient to a real, repeatedly-hit constraint: 20+ scenario instances mean up to 100 sequential LLM calls, enough to burst past Groq's per-minute token budget even on a freshly-issued key, since the limit is tied to the account, not the specific key (confirmed directly from the account's own error responses). Added retry-with-backoff, then a skip-and-record path for when retries are also exhausted, so a real quota wall degrades the harness's output honestly instead of crashing it or silently miscounting an unknown outcome as a confirmed miss. A clean, complete run: baseline recall 80%/precision 100%/mean lead time 42.4 min; full pipeline recall 56%/precision 82%/FPR 12%/mean lead time 58.7 min — the pipeline's lower recall and real false positives, alongside its longer lead time, is a genuine, disclosed finding (the novelty path sometimes convenes the Council earlier than rule/threshold would have, at a point where the evidence is real but not yet dramatic enough for the LLM to call HIGH), not smoothed over.

**Confidence calibration**: reliability diagram bucketing held-out verdicts by stated confidence against empirical accuracy, reusing the harness's own true/false-positive distinction. New Evaluation Report tab (a modal, reachable from the top bar) renders it as a hand-rolled SVG scatter plot against a reference diagonal — no charting library needed for one plot. A real layout bug surfaced verifying this in a browser: the modal was trapped inside the top bar's own `backdrop-filter` containing block instead of the viewport (a CSS fact — `backdrop-filter` creates a new containing block for `position: fixed` descendants), fixed with a React portal to `document.body`.

**Self-improving memory loop**: the hardest single piece of this step. Getting a similarity metric that actually discriminates a genuine near-miss recurrence from ordinary noise took several real, failed attempts, each checked against the real library rather than assumed: a text-embedding approach failed outright (a sentence-transformer mostly captures template phrasing, not the filled-in values — an unrelated negative control scored 0.998 against a genuine match); numeric joint-evidence vectors fared better under cosine similarity, then Euclidean distance, then Mahalanobis distance searched across an entire run — all three hit the same wall, that several negative controls' own noise sits closer to a stored exemplar than a genuine held-out recurrence does. No threshold perfectly separates the classes; this is disclosed as a real, honest limitation, not hidden. Settled on Mahalanobis distance with a threshold (0.65) calibrated to catch both held-out S5 seeds at the cost of a measured, disclosed false-positive rate on four specific negative controls. A second real gap surfaced once the full experiment actually ran: the retrieval trigger correctly decided *when* to convene the Council, but the Chair never received *why* — fixed by threading a `memory_context` field through the LangGraph state and the Chair's prompt, the same way the Override note already flows through. Ran the full held-out before/after experiment for real: false-negative rate went from 50% to 30%, and both held-out S5 seeds specifically flipped from missed to correctly caught via the `memory_retrieval` trigger reason — the actual proof this feature exists to produce. Some of the movement in the aggregate number is real LLM-call variance on unrelated S1 cases (the Chair isn't perfectly deterministic even at low temperature), confirmed by re-running and reported plainly rather than attributed entirely to the memory loop.

**Open Challenge**: five curated (zone, source_shape, permit_type) combinations, each genuinely different from S1-S5's own and from each other, assembled live from the config-driven scenario engine. Real tuning constraint found: in a high-hazard zone, the permit-conflict rule fires at CAUTION the moment any permit is active, almost always beating the novelty path to the trigger — two combinations originally placed in Z1/Z7 had no real room to prove novelty mattered, and a permit-free variant in the same zones produced evidence too thin for the Chair to escalate past CAUTION. Replaced with medium-hazard-zone combinations instead, where the rule requires HIGH, giving novelty a genuine, verified lead.
